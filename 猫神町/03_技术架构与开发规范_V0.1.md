# 《猫神町》技术架构与开发规范 V0.1

> 文档性质：技术选型、系统架构、AI 职责边界与实现规范  
> 当前状态：初步方案，供网页 Demo 与 Unity 客户端开发共同遵守  
> 关联文档：《00_核心玩法与世界规则_V0.1》《01_AI_NPC架构与提示词规则_V0.1》《02_美术风格与2D表现规范_V0.1》  
> 暂定技术组合：DeepSeek 负责运行时对白与选择候选；纯网页承担玩法 Demo 客户端；Unity 承担正式客户端；GPT 负责策划辅助与美术资产生成  
> 非本文范围：开发排期、人员分工、人天估算、里程碑顺序、发布日期和交付批次

## 一、当前结论

明确分工如下：

- **DeepSeek**：游戏运行时生成 NPC 对白、NPC 反应、玩家选项候选、记忆摘要候选和第七天结局文本候选；
- **纯网页 Demo**：最快验证地图、对话、背包、赠送、世界规则、时间推进和人物关系变化；
- **Unity**：承担正式版 2D 场景、Q 版人物、立绘、音频、转场、动画和多平台发布；
- **GPT**：作为离线开发工具，协助策划、结构化角色设定、提示词维护、文档和美术资产生成；默认不作为首版玩家运行时必须调用的模型；
- **独立游戏后端**：保存世界事实、调用模型、校验输出并保护 API Key；网页与 Unity 都不能直接调用模型服务。

核心原则为：

> Demo 可以换客户端，但世界数据、AI 协议和游戏结算规则不能跟着重写。

## 二、客户端技术选型：纯网页 Demo 与 Unity

本作首个 Demo 的主体是界面和状态，而不是实时物理、自由移动或高复杂度动画：

- 点击地点；
- 显示当前在场人物；
- 进行选项式对话；
- 打开背包并赠送任意物品；
- 把物品备份进世界规则；
- 推进每日时间；
- 查看 NPC、地点与关系变化；
- 生成第七天结局。

这些内容使用浏览器的 HTML、CSS 和普通 2D 图片即可完成，不需要先建设完整游戏引擎表现层。

### 2.1 纯网页与 Unity Web 的比较

| 项目 | 纯网页 Demo | Unity Web 构建 |
| --- | --- | --- |
| 对话、背包、地图和状态 UI | 直接使用网页组件，迭代快 | 需要在 Unity UI 中搭建 |
| 分享测试 | 上传后直接发链接 | 也可发链接，但需要构建和正确托管 |
| 修改文案与数据 | 刷新页面即可验证 | 通常需要重新构建 Player 或资源包 |
| 调用后端 API | 浏览器标准 HTTP 请求 | 可调用 HTTP，但需处理 Unity Web 平台限制 |
| 首次加载 | 可按页面和资源渐进加载 | 通常需要先加载 WebAssembly 与游戏数据 |
| 正式版演出扩展 | 能做，但不是本项目理想终点 | 更适合 2D 动画、音频、场景和正式发布 |
| 向正式版迁移 | 客户端界面需要重做 | 如果一开始就用 Unity，客户端可直接延续 |

Unity 官方说明 Web 构建运行在 WebAssembly/WebGL 环境中，并存在文件系统、网络、调试、多线程、音频和性能方面的限制。对于本作，这些限制并非不可解决，但会给轻量玩法原型增加额外技术工作。参考：[Unity Web 技术限制](https://docs.unity3d.com/cn/current/Manual/webgl-technical-overview.html)、[Unity Web 性能注意事项](https://docs.unity3d.com/cn/current/Manual/webgl-performance.html)。

因此当前建议是：

> 第一版不要把“网页版”理解成 Unity 导出的网页包，而是直接制作轻量的纯网页游戏 Demo。

### 2.2 Unity 更适用的技术条件

出现以下需求时，Unity 比纯网页更适合作为客户端技术：

- 核心循环已经通过纸面或其他原型验证；
- 团队已经非常熟悉 Unity 的 2D 和 UI 开发；
- Demo 的目标主要是展示演出而不是验证玩法；
- 必须立刻测试 Q 版人物动画、音频、转场或手柄输入；
- 明确无法接受后续重做网页客户端界面。

当前《猫神町》的 Demo 以对话、选项和状态 UI 为核心，因此客户端技术暂定纯网页；正式表现层技术暂定 Unity。这是职责选择，不代表具体开发时间和先后排期。

## 三、整体技术架构

```text
离线内容生产
GPT（策划、文档、美术生成）
    ↓ 人工审核后写入
角色设定 / 世界规则 / 对话模板 / PNG 资产

玩家运行系统
网页客户端（Demo）或 Unity 客户端（正式版）
    ↓ HTTPS + JSON
游戏后端 API
    ├─ 世界状态与规则结算器
    ├─ 时间与事件调度器
    ├─ NPC 记忆管理器
    ├─ AI Prompt 组装器
    ├─ AI 输出校验器
    ├─ 存档与日志
    └─ 模型供应商适配层
             ↓
          DeepSeek API
```

### 3.1 权威状态

游戏后端是唯一权威状态来源，负责：

- 当前日期与时间段；
- 玩家位置和行动次数；
- NPC 当前地点；
- 物品是否存在、归谁所有、是否损坏；
- 世界规则当前内容和生效顺序；
- NPC 关系、情绪、目标与记忆；
- 哪些事件已经发生；
- 第七天结束条件；
- 哪些信息玩家已经知道。

DeepSeek 不能直接修改这些数据。模型只能提交“对白或行动建议”，由系统校验并决定是否执行。

## 四、各技术的职责边界

### 4.1 DeepSeek：运行时 NPC 与文本生成

DeepSeek 适合承担：

- 根据角色人设和当前状态生成短对白；
- 根据场景生成 2～4 个玩家对话选项候选；
- 给出 NPC 对物品和世界规则的即时反应；
- 提议 NPC 下一步行动；
- 生成事件后的记忆摘要候选；
- 在系统提供全部最终事实后，生成第七天结局叙述候选。

DeepSeek 不承担：

- 判断玩家是否仍拥有某件物品；
- 决定时间是否足够；
- 凭空移动 NPC；
- 凭空创造或复制物品；
- 判断谁真正看见、听见了事件；
- 修改世界规则；
- 直接写入存档；
- 决定第七天是否已经结束。

DeepSeek 官方 API 当前兼容 OpenAI/Anthropic 格式，并提供聊天接口。技术实现必须通过供应商适配层调用，不能把某个模型名称散落在游戏业务代码中。参考：[DeepSeek API 快速开始](https://api-docs.deepseek.com/)。

### 4.2 GPT：离线开发工具，不是首版运行时依赖

GPT 主要用于离线内容生产：

- 协助整理策划文档；
- 把人物故事转成结构化角色档案；
- 设计物品、世界规则和事件候选；
- 检查角色设定与事件是否矛盾；
- 编写并维护角色、场景纯文生图提示词；
- 生成角色母版、表情、Q 版和地点背景候选；
- 为代码、数据表和测试提供辅助。

生成结果必须经过人工选择和审核，再以普通文本或图片资产进入项目。游戏客户端不应在玩家游玩时临时生成角色立绘或地点背景。

如果建设自动美术管线，可以在独立开发工具中使用 GPT Image。当前官方模型支持图像生成与编辑，并可以使用固定模型快照提高生产一致性。参考：[GPT-Image-2 官方说明](https://developers.openai.com/api/docs/models/gpt-image-2)。

### 4.3 网页客户端：玩法验证界面

网页客户端只负责：

- 显示主地图和地点；
- 显示地点背景与 Q 版角色；
- 显示对话、选项与情绪立绘；
- 显示背包与赠送界面；
- 显示猫神社规则槽；
- 显示时间、日志和世界变化；
- 把玩家操作发送到后端；
- 根据后端结果更新画面。

网页客户端不能保存模型密钥，也不能自行决定游戏结果。

### 4.4 Unity：正式表现层

Unity 客户端继续使用相同的后端 API 和 JSON 数据协议，并实现正式表现层：

- 使用 C# 实现客户端流程；
- 加载正式地点背景、Q 版人物和精致立绘；
- 增加音频、转场、特效和基础动画；
- 建设正式存档 UI、设置和多分辨率适配；
- 根据目标平台制作桌面或其他正式版本。

Unity 客户端不能重新实现一套不同的世界规则，否则网页验证结果将失去意义。

## 五、推荐的 Demo 技术栈

### 5.1 前端

- TypeScript；
- React；
- Vite；
- HTML/CSS 负责地图、对话框、背包和规则界面；
- 普通图片图层或简单 Canvas 负责地点背景与 Q 版人物排布；
- 不在首版引入复杂 WebGL、物理引擎和自由移动框架。

### 5.2 后端

- Node.js + TypeScript；
- Fastify 或同等轻量 HTTP 框架；
- Zod 或 JSON Schema 用于请求和 AI 输出校验；
- SQLite 用于单机开发和小规模测试；
- 后续部署时可以换成 PostgreSQL，但不作为首个 Demo 前置条件。

### 5.3 共享协议

前端、后端和未来 Unity 客户端共享版本化 JSON Schema：

- `CharacterState`；
- `WorldRuleState`；
- `ItemState`；
- `LocationState`；
- `DialogueRequest`；
- `DialogueResult`；
- `EventResult`；
- `SaveGame`。

Unity 使用根据同一 Schema 定义的 C# DTO，不自行猜测或扩展字段含义。

## 六、DeepSeek 接入方案

### 6.1 模型配置

模型名称必须放在服务端配置中：

```text
DIALOGUE_PROVIDER=deepseek
DIALOGUE_MODEL=<当前通过评测的模型别名或快照>
DIALOGUE_TIMEOUT_MS=<超时时间>
DIALOGUE_MAX_RETRIES=<重试次数>
```

不在文档中永久锁死某一代模型。每次更换模型都要用同一组代表性场景重新评测：

- 人设稳定性；
- 世界规则服从度；
- 对物品的反应质量；
- 多人关系理解；
- JSON 合法率；
- 延迟；
- 单轮成本；
- 安全与拒答表现。

### 6.2 首版请求方式

首版建议：

- 使用非流式请求；
- 要求结构化 JSON 输出；
- 明确把“请输出 JSON”写入 system 或 user prompt；
- 对返回值做 Schema 校验；
- 校验失败后最多进行有限次数修复重试；
- 重试仍失败时使用人工编写的保底对白；
- 正式显示前过滤模型可能生成的内部字段。

DeepSeek 官方 Chat Completions 接口支持 JSON Output、SSE 流式输出、工具调用和 strict 工具模式；官方同时提醒，使用 JSON Output 时仍需在提示词中明确要求 JSON。参考：[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。

### 6.3 为什么首版不使用流式对白

本作对白不是单纯显示一段自由文本，而是要同时得到：

- NPC 台词；
- 玩家选项；
- 情绪；
- 行动建议；
- 记忆候选；
- 调试信息。

等待完整 JSON 后统一校验更安全。等协议稳定后，可以只把已经通过安全拆分的可见台词字段做打字机效果，不需要真正流式接收模型文本。

### 6.4 推荐输出结构

```json
{
  "npc_line": "显示给玩家的短对白",
  "emotion_id": "guarded",
  "player_choices": [
    {
      "choice_id": "ask_about_shrine",
      "label": "询问神社的变化",
      "intent": "investigate"
    }
  ],
  "npc_action_proposals": [
    {
      "action_type": "leave_location",
      "target_id": "location_clinic",
      "reason": "avoid_player"
    }
  ],
  "memory_candidates": [
    {
      "subject": "player",
      "summary": "玩家追问了神社的新供物",
      "importance": 2
    }
  ],
  "debug_tags": ["rule_callback", "item_suspicion"]
}
```

所有 ID 必须来自后端本轮提供的允许列表。`npc_action_proposals` 和 `memory_candidates` 都只是候选，不会直接写入状态。

### 6.5 Prompt 顺序与缓存

请求内容按“稳定在前、变化在后”的顺序排列：

```text
固定安全与输出规则
固定世界观摘要
固定角色核心人设
固定可执行动作定义
本章背景
当前世界规则
角色当前状态与记忆
本轮场景和玩家选择
```

这样既方便调试，也有利于重复前缀命中缓存。DeepSeek 官方文档说明上下文缓存默认开启，后续请求完整复用已有前缀时可能命中缓存，但命中属于 best-effort，不能把游戏正确性建立在缓存必定命中上。参考：[DeepSeek 上下文缓存](https://api-docs.deepseek.com/guides/kv_cache/)。

## 七、NPC 记忆与上下文管理

不能把整个七天聊天记录原样不断发送给模型。后端应维护四层数据：

1. **角色核心设定**：身份、性格、目标、秘密和行为边界；
2. **当前状态**：地点、关系、情绪、物品与短期目标；
3. **结构化记忆**：角色真正看见、听见、得到或误解的事件；
4. **近期对话窗口**：只保留当前场景需要的少量原文。

长对话结束后由系统生成摘要候选，再由规则检查后写入。记忆条目至少包含：

```json
{
  "memory_id": "mem_0001",
  "owner_id": "npc_doctor",
  "day": 2,
  "source": "witnessed",
  "subject": "player",
  "summary": "玩家把旧手术刀送给了医生",
  "belief_status": "believed_true",
  "importance": 3
}
```

模型不能拥有系统没有提供的全知记忆。

## 八、单轮对话的运行流程

```text
玩家选择一个选项或赠送物品
    ↓
后端校验行动是否合法
    ↓
世界系统生成“已经确定的事实”和允许动作列表
    ↓
Prompt 组装器读取必要角色设定、规则与记忆
    ↓
DeepSeek 返回结构化候选
    ↓
Schema 校验 + ID 白名单 + 长度与内容检查
    ↓
世界系统决定哪些行动和记忆真正生效
    ↓
写入事件日志和存档
    ↓
客户端显示对白、表情、物品去向和下一组选项
```

如果模型超时或返回无效内容：

1. 进行一次相同请求重试；
2. 进行一次缩短上下文的修复请求；
3. 使用该角色与场景的保底对白；
4. 记录错误，但不让玩家存档损坏或卡死。

## 九、安全与密钥管理

- DeepSeek 和 OpenAI/GPT 的 API Key 只能保存在服务器或开发者本机环境变量中；
- 浏览器 JavaScript、Unity 客户端、资源包和公开仓库中不得出现密钥；
- 客户端只能访问自己的游戏会话；
- 所有写入存档的请求必须经过后端鉴权与状态校验；
- 为每个会话设置模型调用频率、并发和费用上限；
- 日志中不保存完整 API Key、系统密钥或不必要的玩家隐私内容；
- 不记录或向玩家展示模型隐藏推理；
- AI 输出视为不可信输入，必须像外部用户输入一样校验和转义。

## 十一、测试与验收规范

### 11.1 AI 稳定性

- JSON 解析成功率；
- Schema 校验成功率；
- 非法 ID 出现率；
- 角色出戏率；
- 凭空知道秘密的比例；
- 物品和世界状态矛盾率；
- 平均响应时间与超时率；
- 每个完整周目的模型成本。

### 11.2 Demo 玩法

- 玩家是否理解地图只显示地点；
- 玩家是否理解赠送后物品永久离开背包；
- 玩家是否注意到规则影响了不同 NPC；
- 玩家是否愿意重新拜访人物寻找 callback；
- 玩家是否能在第七天结局中认出自己的行为后果；
- 没有自由输入时，玩家是否仍然感到选择足够；
- AI 失败时，游戏是否仍能继续。

## 十二、当前确认项

- 运行时 NPC 对白基础模型供应商暂定 DeepSeek；
- DeepSeek 只生成候选，不持有世界真相；
- 首个可玩 Demo 优先使用纯网页，而不是 Unity Web 构建；
- 正式客户端计划使用 Unity；
- 网页与 Unity 复用同一后端、世界规则和 JSON 协议；
- GPT 负责策划辅助和美术生成，生成结果经人工审核后作为静态资产进入项目；
- 所有模型调用都通过后端；
- 首版 AI 返回采用非流式结构化 JSON；
- 游戏在模型失败时必须拥有保底路径。
