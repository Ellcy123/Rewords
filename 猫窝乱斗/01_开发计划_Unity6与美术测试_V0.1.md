## 4. 各阶段任务

### P0：先明确影响全工程的规则

1. 舒适度如何影响战斗、评分和通关；本计划不擅自选择最终答案。
2. 每关时间限制作用于布置、战斗还是整关，以及暂停、广告与超时的处理。
3. 方形盒子初始尺寸、扩容档位与金币购买方式；始终保留方形外轮廓。
4. 猫姿势的离散占格、旋转中心、冲突回退、邻接判定。
5. 猫成长分为哪些局内/局外部分，以及是否改变占地或解锁姿势。
6. 组合类型与战斗最小规则：触发时机、冷却、目标、重复触发和叠加上限。
7. 首轮关卡长度和失败/复活规则；如设置 Boss，在此确定其功能。

交付：规则文档、界面草图、数据字段、3 猫/6 物品样本。10/20 的完整名单在 P4 前完成，不先批量画未定机制的猫。

### P1：Unity 与可复现开发环境

- 采用 2D 工程和正交视角，采用已确认的竖屏触摸布局，同时支持鼠标调试；参考画幅 1080×1920，适配不同竖屏比例与安全区域。
- 采用简单 Sprite 表现 + UI；是否需要 URP 2D 灯光由样板效果决定，不为品质感盲目增加渲染复杂度。
- 逻辑层与 Unity 表现分离：格子、关系、货币、战斗时钟在数据层计算，动画消费结果。
- 静态定义与运行状态分离，避免游戏中修改共享资源污染其他猫。
- 规则用 C# 数据模型；配置通过 ScriptableObject/可导入表维护，选定一个权威编辑源，避免双份数据分叉。
- 分开 Runtime、Editor、EditMode Tests、PlayMode Tests 程序集。
- 固定随机种子和事件日志，为组合错误、数值复现提供依据。
- 管理版本：提交源代码、资源与 `.meta`、Packages 和 ProjectSettings；忽略 Library、Temp、构建缓存。大图的存储/LFS 根据现有仓库决定，不重置父项目仓库。
- 建立批量导入与构建方法、测试调度脚本、日志目录和开发说明。

### P2：灰盒先证明能玩

- 方形棋盘、占格轮廓、拖动吸附、旋转、切换预设姿势、无效操作回退。
- 邻近提示、组合高亮与技能解释，不能只显示一个不明来源的数值。
- 金币、商店购买和扩容；购买事务保证扣款与获得内容一致。
- 轻量自动战斗状态机、关卡开始与结束、计时、胜负。
- 最小成长、通关奖励、失败和模拟复活入口。
- 开发调试面板显示格子、关系、触发来源与随机种子，正式界面隐藏。

先以 3 猫/6 物品覆盖不同形状、至少两种姿势、关系和组合，不降低最终 10/20 要求。用简单图形占位，不等整套美术完成才开始程序。

### P3：建立可复用的美术样板

- 把 1 个盒子、3 只猫、6 件物品及主界面换为目标美术。
- 制作拖拽、落位、姿势切换、联动、受击/治疗、升级与结算反馈。
- 姿势采用预绘变体，先使用短过渡、缩放与轻微弹性，不默认做逐帧全动画或柔体模拟。
- 样板必须在游戏实际显示尺寸下清楚，不能只在大图里漂亮。
- 记录每只猫的生成、修图、导入与返工时间，按实际产能重估 P4。

### P4：扩展至完整内容池

- 填完 10 种猫咪的定位、姿势、关系、成长与组合。
- 填完 20 种物品，覆盖不同组合用途，避免仅数值不同的重复内容。
- 批量生产美术，沿用样板规范，分小批导入。
- 配置敌人、关卡和可选 Boss；数量依 P0 设计确定，不默认要求大型怪物图鉴。
- 建立组合清单及触发预期；明确每种内容在哪些商店池或解锁条件出现。
- 验证新内容不会造成不可能摆放、无效果技能或无尽触发循环。

### P5：完整体验打磨

- 首局分步教学：摆猫 → 姿势 → 物品联动 → 购买扩容 → 战斗/限时。
- 表现反馈：选中轮廓、有效/无效位置、技能范围、舒适度来源、战斗结果。
- 基础音频：落位、购买、猫叫、组合触发、胜败；先用来源明确的占位音效，音频生产不默认附加付费服务。
- 存档：局内快照、局外成长、设置、版本字段与损坏恢复；明确广告/复活事务的保存节点。
- 模拟广告支持成功、取消、失败、超时、重复回调；只有满足奖励条件才发放，且同一事件最多一次。
- 简单事件记录：进入、购买、扩容、姿势切换、失败原因、广告入口与结果，用于后续判断难度和广告需求。
- 测试不同屏幕比例、安全区域、较低帧率、暂停恢复与切后台；设备矩阵在平台确定后补齐。

### P6：交付

- 10/20 内容完整性、核心循环、广告状态、存档、计时、成长、全量组合回归。
- 完成与目标构建对应的交互和性能检查；无图形模式不能代替视觉验证。
- 输出本机可用的构建包、版本与操作说明、测试报告和已知问题。
- 冻结用于演示的配置，保证演示版本可复现。
- 本地 Demo 完成不等于已接入真实广告、通过平台审核或完成上线。

## 5. 美术生产规格与工作量

建议首版每只猫 2 个预设姿势，后续再扩展；这是排期假设，不是已锁定的玩法规格。旋转由程序实现，无需每个角度重新出图。

| 资产 | 首版规划 | 生产方式 |
| --- | --- | --- |
| 风格母版 | 2–3 个候选方向，最终选择 1 套 | Midjourney 探索，统一镜头、配色和光照 |
| 猫咪姿势图 | 10 猫 × 2 姿势，约 20 张主体图 | 固定猫设参考，用 image2 做受控变体与修图 |
| 猫咪头像 | 10 个，尽量由主体图裁切复用 | 避免重复生成导致身份变化 |
| 物品 | 20 张主体图 | 分类批量制作，确保大小与材质可区分 |
| 猫窝/盒子 | 1 套可扩容边框和底板 | 以可拼接或九宫格资源适配尺寸，不每档重画 |
| UI | 商店、金币、技能、计时、结算等一套 | 面板可用图像资产；文字与规则图标在 Unity 中独立排版 |
| 成长表现 | 优先少量配饰、标记与特效复用 | 暂不默认每只猫每级都画一套姿势 |
| 战斗/环境 | 小规模敌人和背景素材 | 待战斗形式明确后确定数量 |

生产顺序：定义网格轮廓 → 制作姿势线稿/轮廓参考 → 选定猫设 → 生成姿势候选 → 修正轮廓与身份特征 → 清理背景/边缘 → 导入 → 实机检查。

特别约束：

- 网格轮廓由程序规则确定，不能从 AI 随机轮廓反推一套失控的玩法。
- 提示词记录花色、眼睛、耳朵、尾巴、视角、光向、线条、阴影与目标姿势；同一只猫必须可认出。
- 生成工具不能保证准确格数、透明底或身份一致性；样板阶段预留人工/工具修正。
- 正式素材分原图、工作稿、导出三层保存，记录提示词、参考图、生成入口/版本、资源 ID。
- 导出约定统一像素密度、透明边缘、Pivot、大小和命名；具体分辨率在目标画幅确定后锁定。
- 高分辨率主稿保留在美术目录；游戏只导入适当尺寸的导出资源，统一 Sprite Atlas 与压缩设置。

## 6. 程序模块划分

| 模块 | 职责 |
| --- | --- |
| Board/Pose | 方形格子、购买扩容、占用、旋转、姿势与合法放置 |
| Cat/Item Definitions | 10/20 静态定义、形状、技能与资源引用 |
| Synergy | 邻接与范围检测、喜好/讨厌、组合来源和叠加规则 |
| Economy/Shop | 金币、商品池、购买、刷新/出售（按后续规则） |
| Combat | 固定逻辑时钟、技能触发、目标、伤害/治疗、胜负 |
| Progression | 局内成长与局外持久成长，边界明确 |
| Run/Stage | 关卡流程、计时、暂停、复活、结算 |
| Save | 快照、迁移、事务记录、隔离测试存档 |
| RewardedAds | 模拟提供方/真实提供方共用接口、奖励一次性发放 |
| Presentation | 输入、动画、音效、UI，避免用动画时长决定战斗逻辑 |

不为 Demo 引入网络 PvP、服务器经济、实时柔体、多币种商城或大型经营系统。

### 7.2 分层验证内容

单元测试用明确的小案例验证规则，不用与实现相同的算法生成“预期答案”。随机局面模拟只能辅助发现问题，不能代替真实游玩、视觉与触摸验证。

### 7.3 计划提供的入口

开发阶段由指定测试代理建立/验证以下 CLI 入口；此处仅列计划，脚本尚未存在：

- `tools/test_editmode.sh`：规则测试。
- `tools/test_playmode.sh`：Unity 集成测试。
- `tools/test_content.sh`：内容与资源引用校验。
- `tools/build_demo.sh`：调用编辑器静态构建方法。
- `tools/report_tests.py`：汇总本轮报告，识别失败、零用例、缺失或陈旧结果。

Unity 测试命令模板（不是本轮执行记录）：

```sh
UNITY_EDITOR="/Applications/Unity/Hub/Editor/6000.4.0f1/Unity.app/Contents/MacOS/Unity"
CAT_PROJECT="/Users/m4/project/rewords/猫窝乱斗/unity"
CAT_RESULTS="/Users/m4/project/rewords/猫窝乱斗/TestResults/<本次运行ID>"
mkdir -p "$CAT_RESULTS"
"$UNITY_EDITOR" -batchmode -projectPath "$CAT_PROJECT" \
  -runTests -testPlatform EditMode \
  -testResults "$CAT_RESULTS/editmode.xml" \
  -logFile "$CAT_RESULTS/editmode.log"
```

PlayMode 使用独立的一次调用，将平台改为 `PlayMode` 并分开日志。测试调用不额外加可能提前终止测试的 `-quit`；构建使用专门的 `-executeMethod` 入口与相应退出处理。实际参数与 Test Framework 包版本在 P1 固定。

同一工程的 Editor 与批处理不能争用项目锁；按顺序调度测试与构建，必要时用隔离测试工作副本。测试存档、广告状态与玩家存档隔离。每次运行生成新报告，检查退出码、XML 用例数与失败数；超时、缺报告、零测试均不能视为通过。

无图形模式仅用于适用的纯逻辑任务。渲染截图、拖拽和手机触摸性能需要有图形环境/实际设备；不能用 CLI 全绿宣称画面或手感合格。
