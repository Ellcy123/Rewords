## 2. 现有代码真实情况

审计依据：Assets/CatDemo/FirstLevel.cs、FirstLevelView.cs、Editor/DemoBuilder.cs、Editor/FirstLevelRulesValidation.cs；当前未发现自定义 asmdef、内容配置资产或独立服务模块。

| 部分 | 实际已有 | 缺失与影响 |
| --- | --- | --- |
| 工程 | Unity 6000.4.0f1、本机打包入口、第一关场景 | 无分层程序集，无清楚的模块依赖 |
| 模型 | FirstLevel 普通 C# 类，与 MonoBehaviour 分开 | 同一个类混合商店、棋盘、战斗、奖励；还依赖 UnityEngine.Vector2Int |
| 猫与用品 | 一猫一用品坐标、姿势布尔值 | 没有定义 ID、实例 ID、列表；不能只配表就增加第二只猫 |
| 棋盘 | 固定 4×4，边界／占用／贴边判断 | 无可变棋盘、扩容、完整暂存管理与多实例去重 |
| 商店 | 买逗猫棒扣 3 金币 | 无货架、商品池、刷新、真实买入价、出售和交易记录 |
| 战斗 | 2 秒／1.25 秒攻击、每三次连击、25 秒限时、奖励防重复 | 数值与技能写死，无多单位、护盾、事件来源或正式状态机制 |
| 流程 | 准备、战斗、完成的几个布尔量 | 无明确状态机、下一关、整局进度；公共字段可被任意写入 |
| UI | OnGUI 绘制、简单鼠标拖动、中文系统字体 | 硬编码坐标和字符串，与输入、状态修改、绘制混在一起；无移动端安全区处理 |
| 存档与广告 | 无 | 退出丢进度；无奖励接口与恢复策略 |
| 测试 | Editor 菜单里的 8 组断言 | 不等于完整 Unity Test Framework 套件或真实 UI 通关；没有 NUnit XML 流程 |

### 审计中需修正的具体问题

- `Cells()` 的“旋转”是交换 x/y，属于转置，不是一般形状的 90 度旋转。直条能换方向，但不能支持全部 L 形朝向。新棋盘要用四向旋转与归一化坐标。
- `FirstLevelView` 在进入后台时直接写同一个 `paused` 变量，恢复前台可能覆盖玩家主动暂停状态。需要分别记录手动暂停、应用暂停和其他阻塞原因。
- `DemoBuilder.Build()` 先调用 Create 重建并保存场景；以后有人编辑场景后，这种打包方式会覆盖内容。场景初始化和日常构建必须拆开，构建只读已配置场景。
- 连击目前是一笔 12 点伤害加文字／闪动，没有独立的三段表现事件；“显示连抓”不等于已做出连击手感。
- 第一关敌人参数较弱，不连用品也可以赢；适合作为无惩罚教学，但过关本身不能证明玩家理解了连接。
- 既有非法落位测试里标为“重叠”的 `(3,2)` 实际会让两格用品越界。需要分别测试重叠和越界，不能用一个失败覆盖两类缺陷。

以上是静态代码审计结论，不冒充已复现的真机测试结果。当前按钮／拖动的真实输入仍要依本轮报告判断。

## 3. 我们采用的结构：四层就够

```text
策划配置（猫、用品、技能参数、关卡、商店、教学）
                       ↓ 初始化与校验
规则层（棋盘、连接、购买、战斗、整局流程）
                       ↑ 操作命令   ↓ 结果与表现事件
Unity 界面层（触摸／鼠标、UI、动画、音效）

存档、模拟广告、时钟作为明确接口接在流程层旁边
```

规则层不读鼠标、不找场景物体、不决定图标颜色。界面请求“把实例 A 放到格子 B”，规则层回答成功或具体失败原因，界面据此显示。CLI 调试与测试可以请求同样的操作，但不能据此声称真实手指操作已通过。

不引入 ECS、大型依赖注入框架、全局万能事件总线、可视化技能编辑器或服务器。依赖由一个启动入口明确创建并传入，避免为了“完整”制造空模块。

## 4. 内容与运行状态分开

### 策划配置：用 Inspector 能改的 ScriptableObject

首版选择 ScriptableObject 为唯一权威配置源，不同时维护一份 Excel 和一份 JSON。后续需要表格编辑时再增加单向导入，明确替换权威源。

| 配置 | 主要字段 |
| --- | --- |
| CatDefinition | 稳定 ID、名字、本地化键、价格、姿势形状列表、基础伤害／间隔、技能 ID 与参数、视觉 ID |
| ItemDefinition | 稳定 ID、价格、形状、目标筛选、效果列表、视觉 ID |
| AbilityDefinition | 触发时机、计数阈值、效果类型与参数、允许的事件来源 |
| StageDefinition | 敌人参数、时限、收入、商品序列／商品池、教学步骤、下一关 ID |
| RunDefinition | 开局金币／猫、棋盘大小、扩容档位、关卡顺序、规则版本 |
| VisualCatalog | 视觉 ID 对应 Sprite／Prefab／音效；找不到时用明确占位并报告 |

加载时转换成只读运行定义，不在游戏过程中改共享 ScriptableObject。新增已支持机制的猫只添加配置；新增一种机制才需要扩展相应效果处理代码，不能承诺所有未来技能零代码。

### 玩家状态：可序列化，使用稳定 ID

- `OwnedInstance`：实例 ID、定义 ID、实际买入价、姿势、四向朝向、位于棋盘还是待摆区、坐标。两只同种猫仍有不同实例 ID。
- `RunState`：局 ID、当前关、阶段、金币、已购实例、棋盘大小、货架、随机状态、刷新与广告次数、已结算记录、教程进度。
- `BattleSnapshot`：开战阵容、有效连接、双方初始属性和技能配置快照；准备阶段变化不能渗入已经开始的战斗。
- `BattleState`：逻辑时间、攻击计时、技能计数、生命、护盾、胜负。战斗临时状态与跨关财产分开。

规则层使用自己的整数格坐标，不依赖 Unity 对象引用；保存定义 ID，不保存场景对象。

## 5. 必须做实的模块与边界

| 模块 | 具体职责 | 完成后能看到什么 |
| --- | --- | --- |
| Board | 多实例占格、四向旋转、姿势、暂存、非法回退、方形扩容 | 两只猫和多件用品可以稳定摆放，不会互相覆盖 |
| Synergy | 目标匹配、贴边、同类去重、一物多猫、来源记录 | 连线来自真实连接，不用界面猜加成 |
| Economy / Shop | 价格、货架、刷新、出售、扩容交易、可用商品筛选 | 改价格不改 C#；失败不会重发资源 |
| Combat | 多猫冷却、基础攻击、连击／重爪／护盾、有限追击、同刻结算 | 首批三种猫可组合运行，动画不影响胜负 |
| RunFlow | 准备→战斗→结果→下一关／重试／整局完成 | 同一套逻辑可跑一关或多关配置 |
| Persistence | 原子保存、版本、备份、恢复与幂等结算 | 关掉重开不丢已购猫，也不重复领钱 |
| RewardedAds | 模拟成功／取消／失败／重复回调，次数与奖励事务 | 可验证广告奖励；真实 SDK 以后替换提供方 |
| Presentation | 竖屏 UI、安全区、鼠标／单指拖动、选择、反馈、占位图替换 | 换正式图无需改技能或棋盘逻辑 |
| Diagnostics | 启动预设、结构化状态、事件日志、CLI 测试／构建入口 | 出错可知道是哪只猫、哪次交易或哪条连接 |

### 状态与交易口径

用一个明确阶段值替换互相独立的 Fighting／Finished／Won 等状态组合。准备阶段才能买卖和摆放，结果阶段只能结算与选下一步；输赢是结果字段，不再到处拼布尔判断。

购买与扩容先校验，再一次性提交余额和获得内容；失败不产生半笔交易。关卡奖励有独立结算 ID，先保存已结算状态再展示结果。所有改变财产的入口都经过流程层，不让 UI 直接改 Gold。

### 战斗扩展口径

保留原来按时间推进、同刻一起结算的思路，但改为多实例调度。时间使用明确精度的整数逻辑单位，避免帧率决定触发次数；精度在实现时统一，首批 1.25 秒与 1.5625 秒都须精确表示。

首批支持伤害加值、攻速加值、开场护盾、每 N 次普攻技能、额外伤害与技能后加盾。效果保留来源实例、目标、原始事件、是否允许再次触发；追加攻击不计入普攻，用品响应不反向递归。

暴击、回复、反伤、持续伤害是后续独立效果类型，预留清楚的接入点，不先做一套未用上的通用技能语言。每种新机制同时增加针对其边界的测试。

### 存档与恢复口径

准备阶段成功交易和摆放后保存；写临时文件后替换，保留最近有效备份，包含 schemaVersion。未知版本／损坏需提示并安全恢复，不能静默删掉进度。

战斗中退出按现有设计从开战快照重新开始；胜利恢复到已发奖结果，不重复发奖；失败重试保留本关商店、广告与刷新计数。系统暂停和主动暂停分开。

## 6. Unity 表现与资源

建议用 Canvas/uGUI 的正式交互结构替代 OnGUI；具体包版本按本机 6000.4.0f1 可用版本固定。采用可序列化场景／Prefab、EventSystem 和统一指针拖放入口，鼠标与触摸走同一业务命令；本轮尚未安装这些 UI 依赖。

暂用一个启动场景和一个游戏界面即可，不为商店、摆放、战斗分别复制一份场景。流程切换面板，数据不跟着面板销毁。

保留临时资源，但用 VisualCatalog 统一引用；准备正式可分发的中文字体，替代仅依赖本机系统字体。声音和效果从战斗事件播放，不从动画回调造成伤害。

后续画风样稿仍按美术目录需求单独处理；架构阶段不顺手扩成正式美术生产。

## 9. 验证与 CLI 分工

所有测试工作由 GPT-6 Luna / xhigh 子代理执行；主代理负责安排、实现和修复。官方 CLI 用于目标工程发现、编译、测试、运行与日志读取，连接包状态与游戏状态分别报告。

必须分别报告：①编译通过；②场景能进入运行；③业务闭环通过；④真实鼠标／触摸输入通过；⑤用户觉得好玩。前一项不能代替后一项。

- EditMode：旋转四次还原、L 形四朝向、越界与重叠独立案例、同类去重、共享用品、购买原子性、技能不递归、时间边界、奖励幂等、存档迁移。
- PlayMode：真实 UI 控件与业务命令联通、拖放预览／回退、面板阶段切换、暂停恢复、场景销毁后无残留订阅。
- 构建：Mac 开发版启动与交互；移动平台确定后再真机验证触摸、安全区和性能。
- 每次运行保存独立日志与有效结果，失败／零用例／缺报告不能算通过；采用 Unity Test Framework 输出标准报告，不把旧菜单断言当成完整测试体系。

## 10. 这轮共同讨论的核心取舍

建议采用：**现在为已确定的 Demo 做可扩展结构，内容和美术仍只从一关开始。** 这避免继续堆硬编码，也避免先花几周造一个什么都没跑的空框架。

默认配置使用 Unity Inspector；如果用户更希望平时在表格里改猫和用品，可把配置编辑入口改为表格单向导入，但不影响上述模块边界。这个选择可在 A 开始前确认，不阻塞本轮审计与 CLI 验证。
