## 1. 项目定位

制作一款有品质感的纯 2D 猫咪空间构筑 Demo，以后续 IAA 上线为目标。玩家在方形盒子内安排猫咪与用品，通过改变猫咪姿势、调整位置和触发邻近组合来构建阵容；利用商店与金币逐步购买内容、扩充空间，并应对轻量战斗关卡。

当前任务只建立项目文件夹、保存基础设定。暂不启动游戏实现，不在本轮擅自确定完整猫咪名单、物品名单、数值或关卡表。

## 2. 已确定的基础范围

| 项目 | 基础要求 |
| --- | --- |
| 表现 | 纯 2D，重视猫咪、用品、盒子的美术品质和反馈 |
| 猫咪数量 | Demo 包含 10 种猫咪；并非同时上场 10 只 |
| 物品数量 | Demo 包含 20 种物品；20 种不包含上述猫咪 |
| 猫咪占地 | 猫咪本身占据格子，具体占格规模参考 Purrfect Fit 后设计 |
| 姿势 | 同一只猫可以切换姿势，改变空间形状；考虑蜷缩、伸展、挤压与旋转的表现 |
| 容器 | 盒子必须保持方形；不采用不规则背包外形 |
| 扩容 | 盒子逐步变大；新增格子需要购买，不按进度免费自动扩容 |
| 商店 | 有商店系统，承接购买、选择和构筑 |
| 货币 | 有金币系统，服务于购买和空间扩展 |
| 邻近组合 | 猫咪与物品临近时能够触发类似背包乱斗的组合效果或技能 |
| 战斗 | 参考背包乱斗的构筑影响战斗、自动结算方向；整体轻量化 |
| 关卡限时 | 每一关都有时间限制；计时阶段、时长与超时处理待定 |
| 广告奖励 | 看激励广告可获得金币或复活次数；额度和次数限制待定 |
| 推进方式 | 基础设置先落档，详细设计逐步推进 |

## 3. 延续前期讨论的设计意图

以下方向保留，但机制和优先级尚未定稿：

- 猫咪有成长，而非只有购买、替换或把相同猫合并。
- 猫咪有喜好，部分猫之间可能喜欢或讨厌彼此，关系影响摆放收益。
- 舒适度曾被提出作为过关条件。本轮新增了战斗要求，因此舒适度与战斗胜负如何结合，必须后续统一设计。
- 商店选择、姿势变化和邻近联动共同构成局内构筑。

不将此前助手举例的猫咪能力、姿势格数、成长路线或天气关卡视为已经确定的需求。

## 4. 参考作品与参考边界

### 4.1 Purrfect Fit

作者页面：https://hoangtd2307.itch.io/purrfect-fit

用户指定参考：

- 猫咪装入盒子的直观表现；
- 猫咪占用格子的规模；
- 盒子逐步扩大的空间节奏；
- 蜷缩、伸展、挤压、旋转等姿势表现。

2026-09-23 核查：作者页面描述了通过蜷缩、伸展、挤压、旋转让猫适应盒子；页面并未公开完整占格表、盒子尺寸序列或具体姿势实现。本轮未实玩，不能把这些细节写成已验证的原作机制。后续空间设计前，需要进一步核对其实际操作与尺寸，再制定本项目规格。

本项目的购买格子、金币商店、邻近组合、猫咪成长和战斗是独立设计要求，不归因于该参考游戏。

### 4.2 Backpack Battles（背包乱斗）

官方页面：https://store.steampowered.com/app/2427700/Backpack_Battles/

参考：商店选择、有限空间摆放、物品联动与组合技能、构筑逐轮成长，以及自动战斗的反馈逻辑。

原作主要是玩家配置之间的 PvP 自动战斗，并非传统单人打怪过关。用户表达了“过关、轻度一点”的意向，因此本 Demo 暂按单人 PvE 闯关方向展开后续设计，不默认要求匹配、排行榜或联网竞技。

具体攻击、冷却、治疗、防御、资源和组合公式尚未选定，不照搬原作完整系统。

## 5. 暂定核心循环

进入本关 → 获得/持有金币 → 商店选购猫咪、物品或扩容 → 摆放、旋转与切换姿势 → 检查邻近组合 → 开始自动战斗 → 胜负结算 → 奖励或复活 → 下一关。

这是后续讨论用的流程骨架，不代表商店开放时机、金币来源、战斗期间能否操作等已确定。

## 6. 空间与姿势设计要求

- 方形盒子是硬约束。暂按宽高相等理解；后续扩容也需要维持方形外轮廓。
- 扩容必须消耗货币。“逐格购买”“整圈扩容”“购买额度后升一档”等方式尚未选择，不能默认采用会把盒子变成不规则形状的方案。
- 初始尺寸、最大尺寸、每次扩容增加多少格、价格曲线均待设计，不冒称来自参考作品。
- 姿势变化应有可辨识的占格预览，猫咪实际占地与画面要一致。
- 换姿势后如何处理冲突、不同姿势是否等面积、切换是否有成本，均待定。
- 首版技术方向优先考虑预设姿势与离散格子，不默认要求 3D 或实时柔体物理；技术方案尚未定稿。

## 7. 邻近组合与成长

确定要有猫咪—物品邻近组合。猫咪—猫咪的喜好关系作为延续设计方向保留；物品—物品组合是否纳入首版，后续确定。

后续需明确：

1. 邻近是否仅指上下左右，是否考虑斜角、朝向、接触边数或技能范围。
2. 组合是持续加成、周期技能、条件触发，还是会消耗材料的合成；这些不能混称为一个机制。
3. 相同效果能否叠加，以及触发顺序、上限和表现。
4. 猫咪成长来源、升级收益、姿势解锁与喜好变化。
5. 哪些成长本局有效，哪些跨局保留。
6. 用品是否升级，以及是否采用配方合成。

10 种猫和 20 种物品需要各自有明确作用，但本轮不先填充占位能力冒充正式内容设计。

## 8. 战斗、舒适度与限时

暂定战斗方向：单人、逐关挑战、布置驱动的自动战斗，减少操作负担。Boss 是否设置、频率和特殊规则待定。

必须先解决舒适度定位：它可能影响战斗能力、独立评分或胜利条件，但尚未选定；不能同时默认“打败敌人”和“舒适度达标”都是硬性通关要求。

每关限时为确定需求，以下细节待设计：

- 倒计时覆盖商店/布置阶段、战斗阶段，还是整关；
- 打开说明、暂停或播放广告时如何处理计时；
- 超时是失败、自动开战还是其他结果；
- 复活恢复的生命、时间、阵容及关卡状态。

这些规则要一起设计，避免购买、思考和看广告相互冲突。

## 9. 金币、商店与广告

金币是基础货币。商店用于购买猫咪、物品和空间扩容。初始金币、过关收益、售价、刷新、出售、库存概率与局内外货币是否共用，均待设计。

激励广告奖励只确定两种：金币、复活次数。本轮不额外加入广告抽猫、广告独占物品、强制插屏或付费商城。

奖励金额、每关/每日次数、复活次数能否储存与携带待定。开发 Demo 时可以先提供明确标注的模拟广告入口，待发行平台确定后再讨论真实广告接入；模拟入口不能宣称产生了真实广告收入。

目标发行平台（微信、抖音或海外 App）尚未确定，当前不宣称通过审核或完成商业化验证。

## 10. 后续详细设计顺序

1. 明确战斗目标、舒适度作用和关卡计时方式。
2. 明确方形盒子的初始尺寸、购买扩容方式与姿势占格规则。
3. 设计 10 种猫咪：形状、姿势、喜好、成长与技能。
4. 设计 20 种物品及邻近组合表。
5. 设计金币、商店和广告奖励的经济循环。
6. 设计敌人、关卡节奏、失败与复活流程。
7. 确定视觉规格、交互和技术方案，再分阶段实现 Demo。

本文件负责记录基础共识，后续详细文档不得无说明地覆盖方形盒子、付费扩容、10 种猫、20 种物品、关卡限时及两类广告奖励等要求。
